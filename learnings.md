The "exactly one inversion" target I gave you was wrong, and the generator proved it by producing absurd pay to satisfy it. The constraint that made the data realistic was capping at range maximum and accepting whatever compression remained.

Nebius routed to first-pass leveling looked fine on paper (fast, cheap) but leveled one notch high on 4 of 5 test cases while reporting confidence 0.85-0.95 on all five — including the one case Claude flagged for escalation. That's a calibration problem, not an uncertainty problem, and no confidence threshold can route around a model that's confidently wrong. Dropped Nebius from leveling entirely; moved it to structured extraction instead, a narrower task that doesn't call for the same adjudication.

Passing the acquisition-level source_org_context to every single employee's leveling call quietly lowered confidence even when the result was consistent with the prior, not contradicting it — an otherwise clean case went from confidence 0.78 (no escalate) to 0.72 (escalate) just by having the context present to reason about. Multiplied across the 25-employee Nyx census, this alone pushed 23/25 employees into escalation, undoing the entire point of adding the Role Summary column in the first place. Isolated by running the same employee, same job description, with and without the context — same level either way, confidence moved anyway.

The old Nyx census generator had a messy-title line, `.replace("MTS L", "Sr MTS ")`, that never matched anything — the title strings it ran against never contained that substring — so the "title variant" it was supposed to inject silently never fired, for the entire dataset, and nobody noticed until the census got rewritten from scratch. A no-op that produces no error and no visibly wrong output is the hardest kind of bug to catch; this one only surfaced because the whole function got read line by line for an unrelated reason.

The equity gate's peer group can't be "same sub-family and same geo" the way check_internal_equity is scoped, or it would almost never find more than one peer at senior levels: L7 is 3 incumbents company-wide in this dataset, each in a different sub-family *and* a different geo. Asked and decided: peer group is the whole family_group at that level, across every geo, compared by compa-ratio (already geo-normalized against each peer's own range_mid) rather than raw salary. Separately, "demonstrably greater scope" in the framework text has no data to back it directly — Meridian's own incumbents don't carry a persisted scope narrative the way the Nyx census does — so it's operationalized as "already holds the level through Meridian's own leveling process." Both decisions made the gate fully mechanical (no open judgment left), so `agents/equity_gate.py` makes no model call at all, unlike the advocate and arbiter.

The Nyx census generator's non-USD "Base" figures (`data/generate.py`'s `NYX_LEVEL_BASE_USD[pay_level] * rng.uniform(0.92, 1.08) * (0.34 if INR else 0.93 if EUR else 1.0)`) weren't real converted local-currency salaries -- that multiplier was the same geo differential number `salary_structures` uses for range adjustment, not a currency exchange rate (USD->INR is roughly x83, not x0.34). NYX-011's recorded "78,760.77 INR" back-solved exactly to 240,000 (Distinguished MTS baseline) x 0.9652 x 0.34 -- a market-level adjustment run through the differential twice, numerically nowhere near a real INR salary (Meridian's own IN-BLR structures run in the millions). Found while building the cost/retention agents (build order item 6). Initially sidestepped by demoing on the census's USD rows only; **fixed on request** by switching `build_nyx_census` to `tools.currency.convert_currency` against `fx_rates.parquet` at `REFERENCE_DATE` (the deal reference date) -- Nyx now pays the same USD-equivalent figure per level everywhere and the local-currency figure is a real dated FX conversion, no geo-differential haircut layered on top (Nyx's own comp story is "consistent USD-equivalent pay," not "discount for lower-cost geos" -- that's Meridian's philosophy, not Nyx's, and NYX_LEVEL_BASE_USD was already documented as deliberately independent of Meridian's geo differentials). Regenerated (`python3 -m data.generate --seed 42`); NYX-011's INR figure is now ~20.2M, in the right order of magnitude. Note this creates a real asymmetry worth knowing about: Meridian's own survey_data/salary_structures still use a fixed `CURRENCY_FACTOR` (not dated FX) -- fixing that is a separate, not-yet-done change to a different part of the generator.

Fixing the above surfaced a second, separate bug in the cost/retention agents themselves: `CostAssessment.total_day_one_cost` and `RetentionAssessment.total_award_day_one` were naively summing each employee's `cost_gap`/`retention_award` across whatever currency that employee happened to be in -- meaningless once a population spans USD/INR/EUR, since raw INR figures are ~80-90x larger in scale than USD ones and would dominate the "total" by unit mismatch alone, not by actual cost. Confirmed directly: a 3-employee USD/INR/EUR population's naive sum came out to 1,103,384.03 against a correct (properly FX-converted, single reporting-currency) total of 71,388.78 USD -- more than 15x off. Fixed by adding `cost_gap_reporting_currency`/`retention_award_reporting_currency` per employee (each converted via `convert_currency` at the deal reference date) and summing those, never the raw per-currency figures, for every population-level total. `CostAssessment`/`RetentionAssessment` now both carry an explicit `reporting_currency` field so the total's unit is never ambiguous.

`lookup_market_data(family_group, level_code, geo_code, ...)` silently blends market data across every sub-family sharing that (family_group, level_code) — job_catalog's `family_group` column only has 3 coarse values (engineering/corporate/gtm), but every job_id has its own distinct `survey_code_primary`. Checked directly: engineering/L5/US-SJC alone joins 9 different job_ids (DD-RTL-L5, ANA-AD-L5, ASW-WEB-L5, ...) into one averaged P50. Never hit before because nothing had called it with a family_group+level_code combo where the blend was consequential. Built `lookup_market_percentile` scoped to an exact `job_id` instead, for the cost agent's per-employee pricing — didn't change `lookup_market_data` itself, since that's an existing, tested, possibly-relied-upon function and fixing it is really the market-pricing-desk workflow's job, not this one's. Worth knowing before anyone reuses `lookup_market_data` believing family_group scopes as narrowly as a specific discipline. Separately: this synthetic dataset's P50 turned out to be numerically identical across all 9 of those sub-families at that particular level+geo, which is why a same-value assertion couldn't distinguish scoped from blended in the test — the row count could.
